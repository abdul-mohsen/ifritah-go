# T016 Daemon-Consumable ZATCA Chain Contract

## Scope

This contract is a backend persistence boundary. It does not define XML
generation, signing, provider submission, retry classification, or debit-note
domain behavior.

The daemon connects to the already-selected tenant database. It MUST NOT
accept a database/table name from an event and interpolate it into SQL.

## Identity

- `branch_id`: positive tenant-local branch ID.
- `egs_id`: trimmed `branch_zatca_config.csr_computer_number`; when empty,
  use `<tenant-id>:branch:<branch-id>` until onboarding supplies the UUID.
- `reservation_key`: T014 `stable_document_key`
  (`tenant:branch:document-type:source-id`).
- `reservation_token`: opaque, unique owner token generated by the caller.

Invoices, credit notes, and debit notes share one chain row for the same
`branch_id` and `egs_id`.

## Required transaction ordering

```text
BEGIN
  ensure/load chain row
  SELECT ... FOR UPDATE
  reserve or recover the same reservation
  COMMIT

generate/sign XML using returned reserved_icv and reserved_previous_hash

BEGIN
  UPDATE ... WHERE branch_id=? AND egs_id=? AND reservation_key=?
    AND reservation_token=? AND reserved_icv=?
  SET last_icv=?, previous_invoice_hash=?, clear reservation
COMMIT
```

The reserve transaction MUST commit before external work. The commit
transaction MUST use the owner predicates in the same update; a prior read
does not grant ownership.

## Reserve result

The result contains:

- `branch_id`
- `egs_id`
- `reservation_key`
- `reservation_token`
- `reserved_icv`
- `reserved_previous_hash` (null/empty for the first chain document)
- `lease_expires_at`

If the same reservation key already owns the row, the operation returns its
existing values without incrementing. If a different unexpired key owns the
row, the daemon waits/retries according to its own policy and MUST NOT steal
the row. An expired owner may be recovered only after the row lock is held.

## Commit/release result

Commit MUST supply the resulting signed-document hash and the expected
reserved ICV. A zero-row result means the reservation is no longer owned and
must be treated as a lost ownership error. Release clears only matching
reservation fields and does not change `last_icv` or the committed prior hash.

## Tenant and live-MySQL limitation

Sqlmock tests verify parameterized SQL, transaction sequencing, and owner
predicates but cannot prove InnoDB row locks, isolation, deadlocks, or lease
expiry. A live MySQL validation is required before production rollout.
