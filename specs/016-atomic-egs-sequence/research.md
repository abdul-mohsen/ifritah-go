# T016 Research

## Repository evidence

1. `pkg/handlers/bill.go` uses `getNextSquenceNumber`, which calls the sqlc
   query `GetMaxSequenceNumber` (`select max(sequence_number) from bill`).
   `AddBill` and `SubmitDraftBill` run inside a transaction, but the global
   max read is not a branch-safe allocator.
2. `pkg/db/migrations/0005_branch_sequence_counters.sql` already creates an
   InnoDB `branch_sequence(branch_id, scope, last_value)` table and a unique
   `(branch_id, sequence_number)` bill index. Its
   `AllocateBranchSequence` sqlc query uses
   `LAST_INSERT_ID(last_value + 1)` with an upsert, which is the existing
   database-native atomic increment pattern.
3. `branch_zatca_config` contains `csr_computer_number` (the EGS UUID),
   `previous_invoice_hash`, and `last_icv`. The schema comment states that
   `last_icv` is shared across bill/credit/debit. The row is currently a
   configuration row and has no reservation owner or lease fields.
4. T014's `Message` envelope already carries tenant, branch, EGS, source
   document, stable key, outbox, and attempt metadata. `buildZatcaOutboxParams`
   serializes the payload before the outbox insert, so the auto-increment
   outbox ID is enriched later by the drainer.
5. `credit_note` currently references a bill and has no independent branch,
   sequence, or ICV columns. The daemon's current credit query derives branch
   and bill sequence through the parent bill. There is intentionally no
   `debit_note` table in this backend.
6. The current backend generated sqlc directory is ignored and contains only
   the checked-in config until `sqlc generate` runs. README explicitly requires
   generation before build/test.
7. Existing sqlmock handler tests expect the global `select CAST(COALESCE(max`
   query, so they provide a focused red baseline and must be updated to expect
   the atomic allocator query.

## Decisions

### D1: Keep invoice number allocation in `branch_sequence`

Use the existing migration/query instead of introducing a second invoice
number table. The unique branch/sequence index remains a last-line integrity
guard, while the upsert serializes normal allocation.

### D2: Add a dedicated EGS chain reservation table

Do not put transient owner/lease/document fields on
`branch_zatca_config`: that row is also read and updated by onboarding and
configuration handlers. A dedicated row keyed by `(branch_id, egs_id)` gives
one clear InnoDB lock owner and allows EGS rotation without mixing old and new
chains.

### D3: Use stable document key for idempotent ownership

The T014 stable document key is already tenant/branch/type/source based and is
durable in `zatca_event_outbox.idempotency_key`. It is therefore the natural
idempotency key for reserve/retry. The reservation table stores it with a
unique constraint.

### D4: Reservation lifecycle is explicit

The SQL contract has four operations:

- reserve-or-get: lock/create the EGS row, reject a different active owner,
  or return the existing reservation for the same document key;
- commit: verify owner/document/expected ICV, write the resulting hash, and
  clear ownership;
- release: verify owner/document and clear a failed reservation without
  advancing the committed chain;
- read-for-update: expose the committed state to a daemon transaction.

The owner token is opaque and must be generated by the caller using a
cryptographically strong value. The backend never treats a tenant or document
ID alone as authorization.

### D5: Keep chain contract separate from daemon behavior

The backend provides SQL and a contract document only. It does not create XML,
hash XML, call ZATCA, process debit notes, or alter daemon code.

## Alternatives considered

1. **Continue using `MAX(sequence_number)`** — rejected because concurrent
   reads race and the result crosses branch boundaries.
2. **Process-local mutex** — rejected because multiple backend instances and
   daemon processes do not share memory.
3. **Lock the branch configuration row forever during XML submission** —
   rejected because external signing/provider work must not hold a database
   transaction open; explicit reservation/lease state is safer.
4. **Use one global EGS row** — rejected because tenant/branch/EGS is the
   isolation boundary and EGS rotation must not reuse a prior chain.
5. **Add a debit-note table now** — rejected because debit domain is explicitly
   out of scope.

## Unresolved operational limitation

Sqlmock can verify query ordering, parameter ownership, rollback handling, and
concurrency-safe application behavior, but it cannot reproduce real InnoDB
row locks, isolation, deadlocks, or lease expiry. A live MySQL integration
test remains required before production rollout and is reported rather than
silently claimed as covered.
